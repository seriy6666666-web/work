## 1. Поднять проект (10 минут)

```bash
git clone https://github.com/seriy6666666-web/work.git belmy
cd belmy
docker compose up --build -d
```

Файл `.env` для разработки **не нужен** — значения по умолчанию прописаны в
`docker-compose.yml`. Приложение: http://localhost:5173, API: http://localhost:3000.
База наполнится демо-данными сама (миграции и сид запускает `backend/docker-entrypoint.sh`).

В логах бэкенда при этом висит предупреждение о слабых секретах — так и должно быть,
это напоминание, что стенд не рабочий. Для запуска на производстве нужен `.env`, см.
раздел «Запуск на производстве» в [README.md](README.md).

Пароль всех демо-сотрудников — `password123`, логины в [DEMO.md](DEMO.md).

### Если нужны сегодняшние данные, а не свежий сид

На **этом** компьютере до отъезда:

```bash
docker compose exec -T postgres pg_dump -U belmy belmy > belmy-dump.sql
```

Перенести файл (флешка, облако — в git не класть) и на ноутбуке:

```bash
docker compose exec -T postgres psql -U belmy -d belmy < belmy-dump.sql
```

Без этого данные будут чистые демонстрационные — для разработки этого достаточно.

## 2. Чтобы кодить, а не только смотреть

```bash
cd backend && npm ci && npx prisma generate
cd ../frontend && npm ci
```

Проверки:

```bash
cd backend && npx tsc --noEmit && npx jest        # типы + 17 unit-тестов
cd frontend && npm run build                      # ОБЯЗАТЕЛЬНО так, не tsc --noEmit
cd frontend && npx playwright test                # 32 сценария, нужен поднятый docker
```

**Важно:** фронт проверять только через `npm run build`. `tsc --noEmit` пропускает ошибки,
которые ломают сборку в Docker — уже наступали на это.

**После `git pull` не забыть `npm ci` и `npx prisma generate`.** `node_modules` и
сгенерированный Prisma-клиент лежат в `.gitignore`, поэтому pull обновляет код, но не их:
получаются ошибки типов про поля, которых «нет», хотя в схеме они есть.

**Не запускать e2e сразу после нагрузочного теста.** Один прогон нагрузки — это 100
входов при лимите 300 в минуту. Два прогона подряд, и тесты падают с невнятными
ошибками вроде `users.find is not a function`: вместо токена приходит 429. Нужна пауза
около минуты.

### Миграции Prisma

`prisma migrate dev` в этом окружении не работает неинтерактивно. Порядок такой:

```bash
cd backend
export DATABASE_URL="postgresql://belmy:belmy_dev_password@127.0.0.1:5432/belmy?schema=public"
mkdir -p prisma/migrations/$(date +%Y%m%d%H%M%S)_имя_миграции
npx prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script > prisma/migrations/<папка>/migration.sql
npx prisma migrate deploy && npx prisma generate
```

`DATABASE_URL` обязателен — без него `migrate diff` падает с `P4003 No URL defined`.
Вывод писать **только** через `>`, без `| head` — обрежет файл на середине и миграция
упадёт с `unterminated quoted identifier`.

## 4. Что решено, но НЕ сделано — продолжать отсюда

### 4.1 Разделение по площадкам — начато, осталась половина

Сделано (`2429baa`, `bfab769`):

- `platformId` у **сотрудника**, **оборудования** и **операции**, все поля необязательные.
- **Списание материалов переведено с площадки заказа на площадку операции.** Это была
  дыра: заказ на одном адресе, сделали на другом — списывался чужой склад. Проверено
  сценарием: заказ на ЮП26, операция на ЮП33, списалось с ЮП33.
- Начальник участка **с адресом** видит только своих по этому адресу — на
  **распределении** и в **матрице компетенций**. Без адреса — весь участок, как раньше.
- Понятное сообщение при попытке назначить своего же человека с другого адреса.
- Демо-площадки переименованы в **ЮП26** и **ЮП33**.

Осталось:

1. **Ограничить остальные экраны** тем же правилом: планирование смен, цели, журнал
   прихода-ухода, статистика, старшие смен, переводы. Распределение и компетенции ходят
   через общий `TransfersService.getEffectiveSiteUserIds(siteId, viewerId)` — там фильтр
   уже есть. Эти пять сервисов запрашивают сотрудников напрямую (`prisma.user.findMany`
   с `where: { siteId }`), поэтому каждый надо провести через тот же помощник или
   добавить фильтр по адресу вручную.
2. **Админка:** поле «площадка» у сотрудника и у оборудования, колонка в списке
   пользователей. Сейчас адрес можно проставить только SQL-запросом.
3. **Начальник производства:** фильтр по адресу в сводке участков.

Как устроено производство (со слов заказчика, не меняется):

- Адреса: ЮП26, ЮП33, скоро ЮП14. Отдельно лаборатория — её пока не трогаем.
- Участки: **призма, цилиндры, заготовки**. Всё. ОТК, лаба, инженеры-конструкторы,
  технолог — отдельные подразделения, в системе их пока нет.
- Призма — на **двух** адресах, ЮП26 и ЮП33, на каждом свой начальник участка.
- Цилиндры — на ЮП33, там начальник участка **и зам начальника участка**.
- Заготовки — физически на ЮП33, снабжают обе площадки.
- Планы: цилиндры целиком переедут на ЮП14, ЮП26 останется под призму. Сроки неизвестны.

**Зам начальника участка** решено не делать отдельной ролью: это второй `SITE_LEAD` на том
же участке и адресе, а в иерархии ему проставляется руководителем начальник участка. Права
те же — зам для того и нужен, чтобы подменять.

**Почему адрес читается из базы, а не из токена.** В токене он лежал бы рядом с участком и
это было бы дешевле, но тогда проставленный админом адрес начинал бы действовать только
после повторного входа — до 12 часов человек продолжал бы видеть чужие площадки. Проверено,
что сейчас смена адреса действует сразу, тем же токеном. Не переносить в токен.

### 4.2 Хвосты

- **HTTPS нет** — пароли и токены идут по сети открытым текстом. Внутри цеховой сети
  терпимо, при доступе снаружи — нет. Нужен reverse proxy с сертификатом (nginx, Caddy,
  Traefik). В README описано, но не поднято. **Единственный оставшийся блокер пилота,
  если доступ будет не только из цеха.**
- **QA-чеклист** ([QA_CHECKLIST.md](QA_CHECKLIST.md)) не пройден целиком.
- **Рассылка событий идёт всем клиентам сразу**, фильтрация по участку на стороне
  браузера. На 100 человек это ничего не стоит (замерено), при подключении всего завода —
  перевести на комнаты по участкам. WebSocket при этом **без авторизации**: подключиться
  может кто угодно и видеть, на каком участке что шевелится.
- **Токен в `localStorage`**, живёт 12 часов, механизма обновления нет. Смену длиннее
  12 часов не переживёт, и уязвим к XSS.
- **Второй экран задач** (`pages/shared/TasksPage.tsx`) и `pages/worker/TasksPage.tsx`
  живут отдельно — при правках задач смотреть оба.

## 6. Договорённости по работе

- **Не начинать писать код, пока заказчик не скажет «поехали».** Сначала предложение,
  потом подтверждение.
- **Качество важнее скорости.** Мелкими порциями, с проверкой каждой. Не расширять один
  заход на всё больше файлов.
- **Браузерное проверять браузером.** `curl` годится для API, но не для CORS, куки,
  редиректов и заголовков. На этом уже наступали: правка CORS полностью закрыла вход в
  приложение, а через `curl` всё выглядело рабочим — поймали только e2e-тесты.
- Прежде чем называть что-то багом — прочитать то место, где он должен быть, целиком.
- Отложенные пункты (импорт материалов, спецификация файлом) **самому не поднимать** —
  заказчик скажет сам.
- После каждого крупного захода — проверка, коммит, пуш и стоп до подтверждения.
- Перед пушем прогонять поиск секретов: `.env`, ключи, дампы в коммит не попадают.

## 7. Что полезно знать про решения, которые уже приняты

- **Пароли.** Админ задаёт вручную или генерирует вида `belmy-7413` — такой диктуют вслух
  и набирают на терминале в цеху. Восстановить пароль нельзя, только задать новый.
- **Импорт разделён по ролям.** Администратор через «Импорт сотрудников» заводит людей и
  получает пароли для раздачи. Планировщик тем же файлом грузит только навыки и
  компетенции уже заведённых людей — учётные записи не создаются, паролей он не видит.
  Раньше планировщик заводил людей десятками и видел их пароли, хотя ему закрыт даже
  список сотрудников.
- **Архив вместо удаления.** Сотрудника с историей производства удалить нельзя — только в
  архив: вход закрывается, из рабочих списков пропадает, в отчётах остаётся. По той же
  причине нельзя снять человека с операции, по которой он уже отчитался.
- **Лимит входов 300/мин.** Вся смена заходит через один шлюз завода. Лимит считается
  **по IP, а не по логину** — за NAT один человек, промахнувшийся паролем много раз,
  расходует общий лимит.
- **Норма выработки** — штук за смену (8 часов). Если человек ушёл раньше, это его дело,
  норма не пересчитывается.
- **Обращения** читает только администратор. Анонимность честная: при галочке автор не
  сохраняется вовсе, остаются роль и участок. **Журнал аудита для анонимных обращений не
  пишет ни автора, ни тело** — иначе администратор сводил бы журнал с обращением по тексту
  и получал автора.
- **Журнал аудита пишет отказы.** Неудачные входы и попытки залезть в чужой раздел
  фиксируются. Guard'ы в Nest срабатывают раньше интерцепторов, поэтому отказы пишет
  отдельный `AuditExceptionFilter`, а не интерцептор.
- **Нативных `<select>` в интерфейсе нет** — везде свой `Select`. У него нет `required`,
  поэтому обязательность полей проверяется в коде страницы; при добавлении новых форм не
  забывать про это. В e2e вместо `selectOption` использовать `chooseOption` из
  `e2e/helpers.ts`.
- **Бэкапы восстанавливаются** — проверено 12.08 на отдельной базе. Версия образа `backup`
  обязана совпадать с версией `postgres`, иначе дамп получается с директивами новых версий.
  Процедура проверки копии — в README.
