# Техническое задание
## Веб-приложение для управления производством ООО «БЕЛМИ» (BELMY ENERGY)

---

## 1. Общее описание проекта

Веб-приложение для планирования, распределения и учёта выполнения производственных операций на предприятии, выпускающем литий-ионные аккумуляторные изделия. Система охватывает полный цикл: от постановки заказа планировщиком до фиксации выполненной работы конкретным сотрудником на конвейере, с последующей аналитикой по выполнению плана.

**Масштаб:** производство свыше 50 человек, несколько участков/смен.

**Важно:** контроль качества (ОКК) в данную систему НЕ встраивается — ведётся отдельно, как сейчас (бумажные/электронные протоколы, акты).

**Премии сотрудникам система не рассчитывает** — только предоставляет данные (рейтинг выполнения плана), на основе которых руководство принимает решения вне системы.

---

## 2. Роли пользователей

Иерархия ролей: **Админ → Начальник производства → Начальник участка → Сотрудник**, плюс независимая роль **Планировщик**.

### 2.1. Администратор
- Технический аккаунт для настройки системы
- Создаёт/редактирует структуру участков (например: «Сварка», «Сборка», «Резка»)
- Создаёт учётные записи всех пользователей, назначает роли и права доступа
- Не участвует в оперативной работе (планирование, распределение и т.д.) — только настройка системы

### 2.2. Планировщик
- Создаёт заказы (например: «1000 батарей до 30 июля»)
- Декомпозирует заказ на операции с указанием количества по каждой, например:
  - Сортировка ячеек
  - Склейка
  - Нарезка шин
  - Нарезка проводов
  - Сварка шин
  - Распайка балансировочных проводов
  - Финальная сборка
- Каждая операция закрепляется за конкретным участком (в стандартном случае — за одним)
- Если операцию выполняют сразу два участка — планировщик указывает общее количество на операцию без разбивки; участки самостоятельно договариваются, кто сколько делает (см. п. 3.8)
- Задаёт горизонт планирования: день / неделя / месяц
- Видит статусы и сроки всех заказов

### 2.3. Начальник производства (главный)
- Видит **всё производство целиком**: все участки, все смены, все операции
- Видит сводную аналитику по каждому участку (% выполнения плана) с возможностью провалиться в конкретный участок и посмотреть детали
- Видит сравнение участков/смен между собой (где отстают, где лидируют)
- Получает автоматические предупреждения, если участок или конкретный сотрудник начинает отставать от плана (риск срыва срока)
- Роль преимущественно наблюдательная/контрольная — не вмешивается напрямую в распределение операций по людям (это делает начальник участка), но видит всё, что происходит на любом участке

### 2.4. Начальник участка
- Видит **только свой участок**: свои операции, своих сотрудников, свою статистику
- Распределяет операции по сотрудникам своего участка, опираясь на матрицу компетенций
- Видит прогресс выполнения плана по своему участку
- Видит рейтинг своих сотрудников по выполнению/перевыполнению плана
- Управляет матрицей компетенций сотрудников своего участка
- Может запросить сотрудника с другого участка на временной основе (см. п. 3.7) — для приёма человека с чужого участка требуется подтверждение начальника принимающего участка

### 2.5. Сотрудник (рабочий)
- Отмечает приход на работу (фиксация времени начала смены)
- Видит свой план на смену: список операций, упорядоченный по приоритету заказа (сначала срочное); порядок может скорректировать начальник участка при распределении
- По каждой операции:
  - Если операция простая — отмечает галочкой «выполнено»
  - Если операция измеримая (штучная) — вводит фактическое количество
- Может исправить свою отметку/количество — не более 2 раз по одной операции (дальше исправление только через начальника участка)
- Видит свою личную статистику выполнения плана

## 3. Функциональные модули

### 3.1. Модуль заказов
- Создание заказа: наименование, количество, срок выполнения, приоритет (устанавливается планировщиком вручную)
- Статусы заказа: создан → в работе → выполнен → отгружен (уточнить точный набор статусов с заказчиком на этапе разработки)
- Система поддерживает произвольное количество одновременно активных заказов
- История изменений по заказу
- Просмотр прогресса выполнения заказа в разрезе всех операций

### 3.2. Модуль операций и планирования
- Привязка операций к заказу
- Указание количества по каждой операции
- Горизонт: день / неделя / месяц
- Возможность корректировки плана

### 3.3. Модуль распределения (для начальника участка)
- Список нераспределённых операций
- Назначение операции на сотрудника (с учётом матрицы компетенций — система должна подсказывать/фильтровать, кто умеет выполнять операцию)
- Перераспределение в течение смены при необходимости

### 3.4. Матрица компетенций
- Бинарная модель на старте: сотрудник «умеет» / «не умеет» выполнять операцию
- Редактируется начальником участка
- Если на операцию не находится ни одного компетентного сотрудника на участке — система должна явно подсвечивать это начальнику участка (индикатор «нет исполнителя»)
- В дальнейшем (не в MVP) — возможность расширения до уровней квалификации (начинающий/опытный/эксперт) или допусков

### 3.5. Учёт отсутствий сотрудников
- Отметка отсутствия сотрудника: больничный, отпуск, отгул/отпуск за свой счёт
- Отсутствующий сотрудник не должен попадать в список доступных для распределения операций
- Кто вносит отметку (сам сотрудник, начальник участка или оба) — уточнить на этапе разработки

### 3.6. Простои и причины невыполнения плана
- Если сотрудник не выполнил план (полностью или частично) — он указывает причину
- Причина выбирается из готового списка (нет материала, поломка оборудования, нет электричества, плохое самочувствие/заболел и т.д.), с возможностью уточнения текстом при необходимости
- Список причин должен разделять зону ответственности: причины «по вине производства/снабжения» (нет материала, поломка оборудования) отдельно от причин «личных» (заболел и т.п.) — чтобы планировщик/начальство видели, чей это «косяк»
- Начальник участка подтверждает или корректирует указанную сотрудником причину
- Причина простоя видна планировщику (если проблема в снабжении/организации — это его зона ответственности) и начальнику производства (в общей аналитике)
- **Влияние на рейтинг:** невыполнение по подтверждённой уважительной причине НЕ должно снижать рейтинг сотрудника — при расчёте статистики такие случаи исключаются или помечаются отдельно
- Точный список причин — согласовать на этапе разработки

### 3.7. Временный перевод сотрудников между участками
- Начальник участка может запросить сотрудника с другого участка на смену/день
- Запрос отправляется начальнику участка, откуда планируется забрать сотрудника — требуется его подтверждение
- После подтверждения сотрудник временно отображается в списке принимающего участка и получает задания оттуда
- По окончании периода перевода сотрудник автоматически возвращается в свой основной участок
- Начальник производства (как видящий всё производство) может видеть все такие переводы, но не обязательно должен их утверждать — решение на уровне начальников участков

### 3.8. Разделяемые операции (два участка на одной операции)
- Планировщик указывает **общее** количество по операции без разбивки по участкам
- Участки самостоятельно координируются между собой, кто сколько выполняет (вне автоматической логики системы на данном этапе)
- Система должна показывать общий прогресс по такой операции (сколько сделано суммарно от общего количества), даже если вклад по участкам не разделяется автоматически
- Автоматическое разделение количества между участками — не в MVP, возможное развитие в будущем

### 3.9. Учёт времени
- Фиксация прихода (кнопка на входе)
- Обсудить на этапе разработки: нужна ли фиксация ухода/перерывов (в ходе обсуждения ТЗ этот пункт остался открытым — уточнить)

### 3.10. Модуль выполнения заданий (интерфейс сотрудника)
- Список операций на смену
- Отметка выполнения (галочка или ввод количества)
- Простой, крупный, понятный интерфейс — рассчитан на использование на цеху (в т.ч. с планшета/терминала)

### 3.11. Модуль статистики и рейтингов
- Рейтинг сотрудников по выполнению/перевыполнению плана (в рамках участка — видит начальник участка)
- Статистика по периодам (смена/неделя/месяц)
- Экспорт отчётов (уточнить формат — Excel/PDF)

### 3.12. Аналитика для начальника производства (сводная, по всему производству)
- Сводные показатели по каждому участку: % выполнения плана
- Возможность провалиться из сводной картины в конкретный участок и увидеть детали (какие операции, кто выполняет, какой прогресс)
- Сравнение участков и смен между собой (рейтинг участков — где отстают, где лидируют)
- История данных за периоды (смена/неделя/месяц) для анализа динамики

### 3.13. Автоматические предупреждения об отставании от плана
- Система отслеживает темп выполнения операций относительно срока по заказу
- Если участок или конкретный сотрудник заметно отстаёт от плана — начальник производства получает предупреждение внутри приложения (визуальный индикатор/раздел «требует внимания»)
- Точный алгоритм расчёта «отставания» (например, % выполнения относительно прошедшей доли времени до дедлайна) — уточнить и определить на этапе разработки
- Внешние каналы уведомлений (Telegram и т.п.) не требуются в MVP — см. п. 4.5

## 4. Технические требования

### 4.1. Платформа и устройства
Приложение должно одинаково полноценно работать на:
- Компьютерах/ноутбуках (офис — планировщик, начальник участка)
- Планшетах/терминалах на цехе (крупные элементы интерфейса, сенсорное управление)
- Телефонах сотрудников

→ Требуется **адаптивный веб-интерфейс** (responsive web app), без установки нативных приложений.

### 4.1а. Смены и график
- График гибкий: у разных участков и разных сотрудников может быть разное время смен
- Система не должна жёстко привязываться к фиксированным «утро/вечер» — время начала/окончания смены определяется по факту отметки прихода конкретного сотрудника

### 4.1б. Архитектура и технический стек (рекомендация)

Технологических предпочтений нет — стек выбирается исходя из надёжности, лёгкости поддержки (систему дальше развивают заказчик + AI-агент) и распространённости. Рекомендация:

- **Backend:** Node.js + TypeScript (Express или NestJS) — популярный, хорошо документированный стек, с которым AI-агенты работают особенно уверенно
- **База данных:** PostgreSQL — надёжная реляционная БД, хорошо подходит для структуры «заказы → операции → назначения → отметки выполнения» со строгими связями между сущностями
- **Frontend:** React + TypeScript, адаptivная вёрстка (одна кодовая база под десктоп/планшет/телефон)
- **API:** REST, с JWT-авторизацией и ролевой моделью доступа
- **Обновление данных:** обычные периодические запросы к серверу (polling раз в 1–3 минуты) — вебсокеты и real-time инфраструктура не требуются, так как мгновенное обновление не критично
- **Контейнеризация:** Docker — обеспечивает одинаковый запуск что локально на предприятии, что в облаке в будущем без переписывания приложения
- Итоговый выбор конкретных версий/библиотек — на усмотрение агента-разработчика при реализации

### 4.2. Сеть и доступность
- На цехе возможны перебои Wi-Fi, но всегда доступен мобильный интернет
- Рекомендация: предусмотреть базовую устойчивость к кратковременным обрывам связи (повторная отправка данных, индикация отсутствия соединения). Полноценный offline-режим не является обязательным для MVP, но архитектуру желательно не блокировать для будущего добавления.

### 4.3. Развёртывание
- **MVP:** локальное развёртывание (на сервере предприятия)
- **Целевое состояние:** доступ из любой точки (облачный хостинг или проброс доступа к локальному серверу через интернет)
- Рекомендация агенту: закладывать архитектуру так, чтобы переход от локального к облачному размещению не требовал переписывания приложения (12-factor подход, конфигурация через переменные окружения, без жёсткой привязки к локальной инфраструктуре)

### 4.4. Авторизация
- Логин/пароль для каждого пользователя
- Ролевая модель доступа: администратор / планировщик / начальник производства / начальник участка / сотрудник
- Права доступа строго разграничены по видимости данных (начальник участка не видит чужие участки; сотрудник не видит чужие задания)

### 4.5. Уведомления
- Внешние каналы (Telegram, email, push) не требуются в MVP
- Внутрисистемные предупреждения об отставании от плана для начальника производства — требуются (см. п. 3.11)
- Заложить архитектурную возможность добавления внешних каналов уведомлений в будущем

### 4.6. Интеграции
- Интеграция с внешними системами (1С и т.п.) не требуется — система автономная, разрабатывается с нуля

## 5. Нефункциональные требования

- **Премиальный уровень исполнения:** аккуратный, современный UI/UX, продуманная визуальная иерархия — не «наколеночное» решение
- **Фирменный стиль BELMY ENERGY** — использовать существующую цветовую палитру бренда:
  - Тёмный фон: `#1A3A4A`
  - Основной зелёный акцент: `#4CAF82`
  - Тёмно-зелёный: `#3D9970`
  - Светло-зелёный фон: `#E8F5EE`
  - Светло-серый фон: `#F4F7F6`
  - Приглушённый серый текст: `#8FA8B0`
  - Основной тёмный текст: `#1A2E3B`
  - (Использовались ранее в презентациях ОКК — уточнить актуальный логотип и точный брендбук при разработке, если он есть)
- Простота использования интерфейса сотрудника — минимум действий для отметки выполнения (расчёт на людей без опыта работы с ПО)
- Производительность: система должна без задержек обслуживать одновременную работу 50+ пользователей
- Русский язык интерфейса

### 5.1. Безопасность и надёжность данных
- Данные производства конфиденциальны — критично защитить с самого начала разработки
- Журнал действий пользователей (кто, что и когда изменил/удалил) — для отчётности и разбора спорных ситуаций
- Регулярное резервное копирование данных
- Разграничение доступа строго по ролям (см. п. 4.4)

### 5.2. Хранение истории
- Срок хранения истории выполненных заданий и статистики — не определён окончательно, решить на этапе разработки. Архитектурно закладывать возможность длительного хранения с последующим архивированием старых данных.

## 6. Открытые вопросы (уточнить в ходе разработки)

1. Точный набор статусов заказа
2. Нужна ли фиксация ухода/перерывов сотрудника или только приход
3. Формат экспорта отчётов (Excel/PDF/оба)
4. Итоговая инфраструктура размещения (облако/локально/гибрид) — на MVP делаем локально, но с архитектурой, готовой к переезду
5. Точный алгоритм расчёта «отставания от плана» для автоматических предупреждений начальнику производства
6. Нужно ли начальнику производства видеть и подтверждать переводы сотрудников между участками, или это полностью на усмотрение начальников участков
7. Будущее развитие разделяемых операций (два участка на одной операции) — стоит ли в следующих версиях делать автоматическое разделение количества
8. Кто вносит отметку об отсутствии сотрудника (сам сотрудник / начальник участка / оба)
9. Точный срок хранения истории данных
10. Актуальный брендбук/логотип BELMY ENERGY, если существует отдельно от найденной цветовой палитры
11. Точный список причин простоя (готовые варианты) и их разделение по зонам ответственности (производство/снабжение vs личные причины сотрудника)

## 8. План поэтапной разработки

Проект разбит на этапы так, чтобы каждый можно было отдавать агенту отдельной задачей — с законченным результатом, который можно проверить, прежде чем двигаться дальше. Не стоит просить агента реализовать всё ТЗ за один заход — контекста не хватит, а качество просядет.

### Этап 0. Фундамент
- Инициализация проекта: backend (Node.js/TypeScript) + frontend (React/TypeScript) + PostgreSQL
- Схема базы данных: пользователи, роли, участки, заказы, операции, назначения, отметки выполнения
- Базовая авторизация (логин/пароль, JWT, ролевая модель)
- Docker-конфигурация для локального запуска
- **Результат:** пустой каркас приложения, в который можно войти под разными ролями и увидеть их разные (пока пустые) интерфейсы

### Этап 1. Администрирование
- Роль администратора: создание участков, создание пользователей и назначение ролей
- **Результат:** админ может создать структуру участков и завести всех сотрудников/начальников/планировщика в систему

### Этап 2. Заказы и операции (планировщик)
- Модуль заказов: создание, статусы, приоритет, сроки
- Декомпозиция заказа на операции с количеством, привязка операции к участку
- **Результат:** планировщик может завести заказ и разложить его на операции по участкам

### Этап 3. Матрица компетенций и распределение (начальник участка)
- Матрица компетенций (умеет/не умеет), редактирование начальником участка
- Индикатор «нет исполнителя» для операций без компетентных сотрудников
- Распределение операций по сотрудникам своего участка
- **Результат:** начальник участка видит операции своего участка и раздаёт их людям с учётом навыков

### Этап 4. Интерфейс сотрудника
- Отметка прихода
- Список заданий на смену (с сортировкой по приоритету)
- Отметка выполнения (галочка/количество), лимит на 2 исправления
- Адаптивная вёрстка под планшет/телефон/десктоп
- **Результат:** сотрудник может отметиться и полноценно работать со своим планом с любого устройства

### Этап 5. Простои, отсутствия, переводы между участками
- Указание причины простоя (список причин + подтверждение начальником участка)
- Учёт отсутствий (больничный/отпуск/отгул)
- Временный перевод сотрудника между участками с подтверждением
- Разделяемые операции (два участка на одной операции, общий прогресс)
- **Результат:** система корректно обрабатывает нестандартные ситуации на цеху

### Этап 6. Статистика и аналитика
- Рейтинг сотрудников по участку (для начальника участка), с учётом уважительных причин простоя
- Сводная аналитика по всему производству (для начальника производства): по участкам, с проваливанием в детали, сравнение участков/смен
- Автоматические предупреждения об отставании от плана
- Экспорт отчётов
- **Результат:** обе управленческие роли получают полноценную картину происходящего

### Этап 7. Полировка, безопасность, премиальный вид
- Фирменный стиль BELMY ENERGY (цвета, логотип), финальный UI/UX-проход
- Журнал действий пользователей, резервное копирование
- Нагрузочная проверка на 50+ одновременных пользователей
- **Результат:** готовый к использованию продукт премиального уровня
